Exact keyboard behavior implemented
-----------------------------------

1. Prepaid mobile number
   - TextInputAction.next is passed to the existing
     CustomCountryPhoneInputRow.
   - Flutter's standard focus traversal moves focus to Confirm mobile number.
   - No FocusNode, manual nextFocus/requestFocus call, raw keyboard listener, or
     onEditingComplete handler was added.

2. Confirm mobile number
   - TextInputAction.next is passed to the existing
     CustomCountryPhoneInputRow.
   - Flutter's standard focus traversal moves focus to the Top-up amount
     TextField.
   - Pressing Next does not submit or validate.
   - No FocusNode or manual focus movement was added.

3. Top-up amount
   - TextInputAction.done is supplied at the Guest prepaid top-up call site.
   - Its onSubmitted callback ignores the submitted String and invokes only the
     shared screen-local Next action.


Shared Next action and latest BLoC state
----------------------------------------

guest_topup_screen.dart now defines one screen-local nextAction callback in the
existing build scope. Every invocation reads:

  context.read<GuestTopUpBloc>().state

and passes that latest state to the existing _handleNextPressed method.

The same nextAction callback is used by:

- DefaultButton.onPressed
- GradientInputField.onSubmitted for keyboard Done

Validation and navigation were not copied into the keyboard callback. Both
entry points therefore retain the exact existing _handleNextPressed sequence:

- first-phone validation and the existing invalid-phone error toast
- confirm-phone empty/mismatch validation and existing mismatch error toast
- digit-normalized phone comparison
- existing amount parsing
- silent return for invalid or non-positive amounts
- context.push(AppRoutes.confirmGuestTopUp) with the existing phoneNumber and
  amount extras

No loading guard, debounce, navigation lock, BLoC event, API call, or other
submission behavior was introduced. The existing always-enabled Next semantics
remain unchanged.


GradientInputField compatibility
--------------------------------

GradientInputField received only these two nullable optional properties:

- TextInputAction? textInputAction
- ValueChanged<String>? onSubmitted

Both default to null and are forwarded unchanged to the existing internal
TextField. Existing callers that omit them, including the logged-in prepaid
top-up caller, retain their previous keyboard behavior.

The private controller, sanitization, dollar-prefix display rewrite, cursor
placement, keyboardType, initialValue behavior, styling, and layout were not
changed. CustomCountryPhoneInputRow was not modified.
