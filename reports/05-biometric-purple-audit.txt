3. Current biometric architecture

- App startup registers one BiometricAuthService, repository, and FingerFaceSecurityCubit, then loads device availability and the saved biometric-enabled flag.
- BiometricAuthService wraps local_auth for hardware/support checks, enrolled types, device-local authentication, and SharedPreferences enablement flags.
- FingerFaceSecurityRepositoryImpl exposes availability as isFaceIdAvailable/isFingerprintAvailable and passes authentication results to the cubit.
- FingerFaceSecurityCubit provides loading/authenticated/failure states and generic messages. BiometricLockScreen automatically authenticates and displays status text with retry.
- The Settings screen enables/disables biometric lock by reusing the same cubit/service. Android biometric permissions and the iOS Face ID usage description are present.
- The Home redirect uses the global cubit's in-memory isSessionAuthenticated flag and biometric availability. It does not check the biometric-enabled flag or validate a JWT itself.
- authenticateWithBiometrics currently defaults biometricOnly to false, so the underlying platform may permit device PIN/passcode/pattern fallback.

4. Login biometric current behavior

- Face ID and Fingerprint buttons both exist and are always visible.
- Both buttons call an empty onPressed callback. They are placeholders: no BLoC/cubit event, biometric service call, availability check, loading state, message, session check, or navigation occurs.
- None of the five required source-sheet messages exists in the scoped Login or biometric code.
- The normal password Login success message is "Logged in successfully"; the reusable lock screen's success status is "Authentication successful!". Neither is biometric Login behavior or the required "Welcome!".

6. Reusable existing biometric flow

- A working device-local biometric mechanism exists and can be reused: BiometricAuthService -> FingerFaceSecurityRepositoryImpl -> FingerFaceSecurityCubit.
- Availability flags can conditionally show Face ID or Fingerprint instead of always showing both buttons.
- The existing cubit supplies authenticating/success/failure states and the lock screen supplies retry behavior.
- The entire Home-boundary lock flow should not be copied into Login unchanged: its guard checks availability rather than enablement, its success is not independently JWT-gated, and its messages do not match the purple requirements.
- Face versus fingerprint availability is partially distinguishable. Authentication success/failure itself is generic and carries no matched modality; selected-button context would be needed.
- Lockout is distinguishable at the local_auth exception boundary but not after the current service mapping.

7. Session/auth dependency findings

- AuthCompletionService persists a MyAliv JWT only after password or OTP authentication. The biometric service never calls AuthCompletionService, AuthManager, or Kansys.
- Splash and ALIV Mobile entry route to Login when the persisted session is missing or refresh-expired; a valid session routes toward Home instead. Therefore the normal Login screen does not have a valid session for biometrics merely to unlock.
- OTP success marks the in-memory biometric session authenticated only after server authentication/session completion. Login biometric buttons have no equivalent authenticated prerequisite.
- The Home biometric guard does not itself prove a valid persisted session and can be reached directly. Its local success must not be treated as sufficient evidence of MyAliv login.
- Result: the failure/lockout messages can be implemented within the current biometric state architecture, but both true biometric-login success tasks cannot be completed safely without a confirmed session model. If the intended behavior is only to unlock a still-valid persisted session, that eligibility rule and Login entry behavior must be defined. If biometrics must create a new session, a backend/credential-binding flow is required and is outside this task.

8. Regression risks

- Changing global cubit messages would also change Home lock and Settings behavior; Login-specific purple copy should be mapped at the Login presentation boundary.
- Treating cancellation, fallback, unavailable hardware, or no enrollment as “not recognized” would show incorrect failure copy.
- Treating local biometric success as login success could expose Home without a valid server session.
- Showing both controls regardless of enrolled modality can launch the wrong labeled flow; generic BiometricType.strong is not sufficient proof of fingerprint.
- Lockout handling must rely on platform codes, not an app-side failure counter, and must leave password login usable.
- Enabling biometric-only authentication or changing fallback behavior globally could alter the existing Home lock/Settings flow.

9. Recommended implementation scope

- Do not implement the success paths until the session/auth questions below are resolved.
- Once confirmed, the smallest likely change set is:
  - lib/app/Aliv-Mobile/login/widgets/login_social_buttons.dart: callbacks, availability-driven visibility, and loading/disabled state.
  - lib/app/Aliv-Mobile/login/view/login_page.dart: listen to the existing biometric cubit, present the five exact Login messages, verify session eligibility, and use existing navigation.
  - packages/feartures/finger_face_security/lib/src/services/biometric_auth_service.dart: preserve cancellation and lockout result distinctions rather than collapsing them.
  - packages/feartures/finger_face_security/lib/src/bloc/finger_face_security_cubit.dart and finger_face_security_state.dart only if needed to expose those existing result distinctions cleanly.
- Reuse the existing repository, dependency injection, local_auth dependency, AppToast/message component, AuthManager, and Home route. Do not create a new biometric system, repository, route architecture, dependency, or client-side attempt counter.

10. Blockers / confirmations needed

- Define biometric “login”: unlock an existing unexpired persisted JWT, or obtain a new MyAliv/Kansys session. Current code supports only local device authentication.
- Confirm why/how a user with a valid persisted session should reach Login, since current Splash/Welcome entry sends that user toward Home.
- Confirm that biometric login is allowed only when the app's saved biometric-enabled/setup state is true; current Login buttons ignore both.
- Confirm handling for cancel and device-credential fallback. They must not be mislabeled as face/fingerprint recognition failures.
- Confirm button behavior on devices exposing both modalities or only BiometricType.strong; the authentication result does not identify which modality succeeded.
- Confirm whether both temporaryLockout and biometricLockout should use the row-57 message. The current dependency exposes both, but the app currently merges them into generic error.
- Confirm the Login message presentation for these rows. The copy is authoritative, but the source-sheet details supplied here do not state toast, inline, banner, or lock-screen presentation.
