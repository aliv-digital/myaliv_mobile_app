1. Executive Summary
====================

Overall verdict: FAIL against the supplied chart in specific conditions, with
ordinary A/B/C and ordinary D behavior matching its business rules. Scenario E
normally has the correct single Future Plan button, but its warning/schedule
date is NOT the current active primary's expiration. It is the latest known end
across primary, standalone, and secondary plans [O:99-123; S:247-262].

Main results (CODE):
1) A/C: with no primary entries, the owner shows immediate-only/no-active-plan
   copy. Guest uses date-based active detection and account-owner pronouns.
   Active standalone entries alone do not cause replacement copy [O:35-36,
   251-287; S:160-162; G:368-453; GS:162-173].
2) B: roaming/roameasy/libertyGlobal tabs always select immediate-or-date sheets
   before current/future-plan evaluation. No first-purchase flag is evaluated
   [O:65-95; G:295-325].
3) D: for ordinary non-MiFi primary purchase, active primary and no future
   primary selects the requested owner description, both buttons and the latest
   primary expiry. It literally says "active your plan" [O:127-167].
4) E: active + future primary with no parseable end anywhere falls through to
   BOTH buttons, violating Future Plan only [O:99-127; G:333-383].
5) Owner's outer `hasActivePlan` means earliest primary entry exists, not
   `hasActivePrimaryPlan`. Expired-only or future-only primary entries can
   wrongly trigger replacement/scheduling descriptions [O:35-36,127-165].
6) Failed existing-plan requests can become a successful-looking no-active-plan
   decision; no separate unknown-eligibility state protects that decision
   [R:159-164; GB:123-129].
7) A MiFi-specific warning deliberately overrides D's description and omits the
   expiry/scheduling explanation, even though both buttons remain [O:145-167;
   G:372-383]. This is a mismatch to the provided generic chart, not proof the
   separately implemented MiFi product requirement is wrong.

Tester verdict: PARTIALLY SUPPORTED. There are concrete paths to wrong/missing
description or date. There is no evidence that the normal valid-data D branch
universally chooses a wrong description. The actual tester account, selected
tab, response, and observed text are unavailable, so that particular occurrence
remains UNCLEAR. No runtime reproduction is claimed.

2.2 Existing-plan mapping and state evaluation

`fetchAddOnsData` -> fetchBundles -> parseBundlesJson -> BundleResponseParser
[R:135-163; lib/app/Plans/PlanScreen/repository/services/plan_parser_service.dart:
124-137; BP:13-44]. Response keys:
  PrimaryPlans    -> addOnsApiPrimaryPlans
  SecondaryPlans  -> secondaryPlans
  StandAlonePlans -> standAlonePlans
Each item becomes BasePlanModel; lists are sorted by parsed StartDate ascending,
with unparseable starts last and stable input order for ties [BP:50-79]. There
is no filtering of expired/current/future entries at this parser boundary.

Fields used for activation choices/date:
  StartDate -> BasePlanModel.startDate -> startDateTime
  EndDate   -> BasePlanModel.endDate   -> endDateTime
  PlanGroup -> MiFi warning override
  PlanType  -> catalog category and downstream purchase context/type
  PlanID    -> selection/deduplication/payment bundle
`CurrentlyAssigned` is parsed but is NOT checked by these activation predicates;
there is no PlanStatus response mapping used in their decision [M:170-205;
S:160-262; GS:109-183]. Primary membership comes from the PrimaryPlans array,
not a second `plan.planType == 'P'` test in the state getters.

Definitions used below:
  E = earliestAddOnsPrimaryPlan != null. Owner earliest is optimistic plan,
      else the first PrimaryPlans entry [S:160-162].
  A = hasActivePrimaryPlan: any effective primary whose local StartDate's DAY
      is not after today (or start is null), AND whose end is null OR strictly
      after DateTime.now() [S:206-217; GS:162-173].
  F = hasFuturePrimaryPlans: any effective primary with parsed local StartDate
      DAY strictly after today [S:226-233; GS:151-159]. End is not checked.
  Lp = latestPrimaryPlanEndDate: max parseable end in effective primary list
       [S:183-190; GS:119-126].
  La = latestPurchasedPlanEndDate: max parseable end in primary + standalone +
       effective secondary (raw secondary for guest) [S:247-262; GS:133-147].
  Rtab = selectedTab in {roaming, roameasy, libertyGlobal} [O:65-67; G:297-299].

`hasFuturePlans` (owner only, broader than F) includes future standalone entries.
It affects fallback wording in `!A && standAlonePlans.isNotEmpty &&
hasFuturePlans` [S:193-202; O:138-164]. It is NOT the schedule-only predicate.
The similarly named `hasActivePrimaryWithStandaloneAndFuturePlans` only controls
diagnostic logging in this entry point [S:221-222; V:178-185,200-202].
The actual schedule-only predicate is `A && F` [S:242-243; GS:182-183].

6. Expiration Date Source & Formatting
======================================

6.1 Exact data chain
Owner device bundles / guest entered-number existingplans -> PrimaryPlans /
StandAlonePlans / SecondaryPlans items -> BasePlanModel.fromApiMap EndDate ->
trimmed String -> endDateTime -> toLocalApiDate -> parseApiDate -> toDeviceLocal
-> Lp or La -> DateFormat('MM-dd-yy') -> warningText -> sheet Text
[API:30-47; GR:159-177; BP:13-43; M:177-178,318-320,400; DX:11,45;
DP:12-53; S:183-190,247-262; O:103-106,128-160; G:339-344,369-382].
It does NOT come from the selected catalog plan's end date in the ordinary live
existing-plan path. Catalog PlanDescription is not used as the activation warning.

6.2 Formatting versus business selection
Popup format is month-day-two-digit-year: MM-dd-yy. Example: a local expiry of
23 November 2026 is "11-23-26". The placeholder XX-XX-XX alone does not specify
day/month order, so it is insufficient evidence to call MM-dd-yy itself wrong.
Confirmation begins text instead uses dd-MM-yy [CR:162-187; GCR:65-83]. The same
23 November date becomes "23-11-26" there: a confirmed cross-screen inconsistency,
not proof the popup selected the wrong plan.

DP treats bare ISO datetime and supported US meridiem format as UTC, applies
explicit offsets via DateTime parsing, then DX converts to the device timezone.
The displayed calendar day can differ from the raw API text near midnight.
That is deliberate conversion by the implementation; correct intended business
timezone requires API contract/device verification. It is not always the literal
calendar date written in the response. ISO parse uses DateTime.tryParse and US
fallback DateTime.utc; neither branch performs explicit strict component-range
validation, so some overflow dates can normalize rather than be rejected.

Normal D: Lp is maximum primary end, not specifically the active entry's end.
With exactly one active primary and no future primary this equals that plan's
API-derived local expiry. If several primaries are present, source selection
does not insist the chosen entry be current/assigned. E uses La, which includes
future primary, standalone and add-on dates. An actually active primary ending
on November 8 and future primary ending December 8 will produce "12-08-26" in
E's "current plan ends" warning; a later standalone end can move it further.
This example is a source-derived illustration, not captured backend data.

6.3 Null / empty / invalid / unavailable date behavior
* Null/missing/empty EndDate -> M._asString returns ''; unparseable supported
  parsing failure -> null endDateTime [M:177-178,318-320,400; DP:13-19,38-39].
* Lp/La ignore null ends and use another valid maximum if available; there is
  no placeholder or visible "date unavailable" error in the popup
  [S:183-190,247-262; GS:119-146].
* D with Lp=null omits the entire ` on DATE` suffix but still offers Future Plan
  with empty futurePlanStartDate [O:40-41,128-130,240-246;
  G:286-287,369-371,411-419]. Owner confirmation then says "begins immediately"
  for empty date despite forceNow=false [CR:149-166]. Owner request factory
  later rejects missing scheduled date [REQ:70-74,113-117].
* E with La=null abandons schedule-only and shows both buttons. This behavior is
  explicitly asserted by T2:353-368 and contradicts the chart's E button rule.
* Missing EndDate can itself make a non-future entry count active: `end == null
  || end.isAfter(now)` [S:215-216; GS:171-172]. Missing/unparseable StartDate
  similarly does not disqualify it from active status. Unknown dates therefore
  affect BOTH the description branch and whether a date can be interpolated.

6.4 Is it always a real API-provided expiry?
No. Owner may have an optimistic plan immediately after purchase. Payment view
uses now for immediate purchases, selectedBeginDate for scheduled purchases,
then injectOptimisticPrimaryPlanChange estimates end from frequency
[lib/app/Plans/homePlansPaymentMethod/view/home_plans_payment_method_view.dart:
185-209; C:197-219]. Daily adds 1 day, weekly 7, monthly one calendar month;
unknown returns null
[lib/app/Plans/PlanScreen/repository/services/plan_frequency_estimator.dart:14-30].
S.effectivePrimaryPlans can include this estimate; earliest may prefer it
[S:160-173]. Thus popup expiry can be estimated until bundles confirms it.
Matching PlanID clears optimistic state; empty returned primaries retain it;
the 30-second clearing check is applied only for nonempty unmatched responses
[C:246,256-277]. Deduplication by PlanID can suppress an optimistic purchase of
the same plan ID already present, so repeated same-plan purchases are not a
distinct subscription identity here [S:167-173]. Guest has no such optimistic
injection in its purchase state [GS:109-125].

9. Tester Bug Investigation
===========================

Reported: Purchase Now -> activation popup, expected choices based on active /
future primary state and expiry in warning; actual "description shows wrong."

Q1: Exactly which conditions can support that report?
* !Rtab && E && !A: owner M6 replacement warning or M7 scheduling warning with
  no currently active primary (F3).
* !Rtab && A && F && La!=null: M5/G5 says current plan ends on future/standalone/
  secondary's later expiry (F1).
* !Rtab && A && F && La==null: dual replacement description despite queued
  primary; immediate option returns (F2).

* MiFi-on-active-MiFi: specific replacement-only M4/G4 instead of generic D

* Existingplans/bundles failure or malformed payload with no retained primary:
  false no-active-plan description if account really has plans (F5).
* Stale/hydrated/optimistic state, open-sheet snapshot, device-local date shifts
  or wrong array placement can also explain discrepancies, but the actual
  triggering account/payload/timezone is RUNTIME REQUIRED (sections 6/8).

Q2: Does the app choose the correct description for every condition?
No: concrete exceptions above. Ordinary A/B/C/D valid-data paths are supported
by source and existing test expectations. Normal D expression is
`hasActivePrimaryWithoutFuturePrimaryPlans` (A&&!F), after Rtab, valid E and MiFi
precedence, and displays M3. That by itself does NOT support a universal wrong
description claim. The typo is real even when selection is correct.

Q3: Can state/API mapping cause a wrong description?
Yes, conditionally and with exact mechanisms: primary list existence used as
active; null dates treated as active; errors mapped to empty; case-sensitive
keys silently absent; cached/optimistic values; broad max-end selection. No
observed production response proves one of these caused this tester incident.

Q4: Is the date from the correct source?
Normally API EndDate parsed local. D's one-current-primary case uses its real
end. E deliberately uses latest of every purchased plan, diverging from supplied
"current plan expires" baseline. Optimistic owner dates can be estimates. The
date is not a random demo date inserted by the activation launcher; null dates
are omitted, and the selected catalog's description is not used for the warning.

Source-level branch reproduction is supported for F1-F7. T1 explicitly encodes
future-only replacement wording, T2 explicitly encodes no-date E dual buttons
and latest standalone/secondary expiry, and T3 encodes MiFi copy without expiry.
These tests confirm intended current expectations in SOURCE; they were not run
and do not prove a live backend response. No screenshot, account payload, tab,
