CREATE PASSWORD KEYBOARD BEHAVIOR AUDIT

Audit scope
-----------
Investigation only. No application code, UI, validation, navigation, business
logic, data flow, or runtime behavior was changed. Line numbers below refer to
the code as inspected for this audit.

2. Input count and current order
--------------------------------

There are exactly two editable input fields, both PasswordInput instances in
create_password_page.dart:

1. "enter new password" (lines 97-106)
2. "re-enter password" (lines 115-124)

Each PasswordInput contains exactly one Flutter TextField
(password_input.dart lines 89-101). The first and second inputs appear in that
order in the same Column, separated by 15 logical pixels. No other editable
control exists on this screen.


3. Current TextInputAction / keyboard action configuration
----------------------------------------------------------

Both fields:

- PasswordInput does not declare or accept a textInputAction parameter.
- Its internal TextField does not set textInputAction.
- It also does not set keyboardType, maxLines, or minLines. TextField therefore
  remains a default single-line text field.
- Because textInputAction is null, Flutter/IME default resolution is used. For
  a default single-line TextField this normally resolves to a completion/Done
  action, but it is not an explicit screen contract and can be represented
  differently by a platform or keyboard.

Consequences:

- The first field does not explicitly advertise Next.
- The second field does not explicitly advertise Done.
- A keyboard completion action currently has no application submission
  callback on either field.


4. Current focus and keyboard-submit handling
---------------------------------------------

PasswordInput focus behavior (password_input.dart):

- Each PasswordInput State creates its own private FocusNode at line 26.
- initState registers _onFocusChanged (lines 29-33).
- _onFocusChanged updates _hasFocus (lines 42-48), which controls whether the
  custom input border shows its focused gradient.
- dispose removes the listener and disposes the FocusNode (lines 35-40).
- The private node is assigned to TextField.focusNode at line 90.
- The FocusNode is not accepted from or exposed to the parent screen.

There is currently no:

- onSubmitted on TextField;
- onEditingComplete on TextField;
- TextFormField/onFieldSubmitted (the implementation uses TextField, not
  TextFormField);
- FocusScope.nextFocus, FocusNode.requestFocus, or explicit focus transfer;
- keyboard-driven call to SubmitCreatePassword.

The default TextField/EditableText completion behavior therefore applies. A
default completion action may release focus/dismiss the keyboard, but it does
not dispatch the screen's SubmitCreatePassword event because no submission
callback is installed.

The containing CustomScrollView uses
ScrollViewKeyboardDismissBehavior.onDrag (create_password_page.dart line 80),
so dragging the view can dismiss the keyboard independently of IME actions.


5. Exact existing Continue-button action
-----------------------------------------

The Continue control is DefaultButton at create_password_page.dart lines
135-147. Its exact onPressed action (lines 142-144) is:

  context
      .read<CreatePasswordBloc>()
      .add(const SubmitCreatePassword())

The button itself contains no validation, repository call, toast, or
navigation logic. It only dispatches SubmitCreatePassword.

The label defaults to "continue" but is configurable through
CreatePasswordScreen.buttonLabel. The callback is present for every status;
the shared DefaultButton prevents invocation only while isLoading is true.
This screen sets isLoading when state.status is CreatePasswordStatus.submitting
(create_password_page.dart lines 140-144). The button is not disabled merely
because the current values are initial or invalid.


6. Current validation and submission flow
-----------------------------------------

Live field updates:

- First input onChanged dispatches PasswordChanged(rawValue).
- Second input onChanged dispatches ConfirmPasswordChanged(rawValue).
- The corresponding BLoC handlers store the raw value, clear errorMessage, and
  run _validate (create_password_bloc.dart lines 20-34).

Live _validate behavior (create_password_bloc.dart lines 91-104 and
create_password_state.dart lines 29-31):

- If both raw values are empty, status becomes initial.
- Otherwise status becomes valid only when:
  - password.trim().length is at least 8; and
  - password.trim() equals confirmPassword.trim().
- All other live states become invalid.
- Live canSubmit does not check the 64-character maximum.
- The Continue button does not consume canSubmit and remains tappable while
  initial/invalid. Validation feedback is produced when submission is tried.

SubmitCreatePassword handling (create_password_bloc.dart lines 50-89):

1. Trim leading/trailing whitespace from both stored values.
2. If the trimmed password is shorter than 8 characters, show the warning
   toast "Password must be at least 8 characters." and return.
3. If the trimmed password is longer than 64 characters, show the warning
   toast "Password must be 64 characters or fewer." and return.
4. If the two trimmed values differ, show the warning toast
   "Passwords do not match." and return.
5. Otherwise emit submitting and clear errorMessage.
6. Call CreatePasswordRepository.createPassword(password: pass).
7. The repository sends POST Api.updatePasswordUrl with:
   {"CurrentPassword": null, "NewPassword": trimmedPassword}.
8. On success, emit success. The screen listener shows
   "Password updated successfully." and executes context.go(AppRoutes.home).
9. On failure, emit failure with the extracted/fallback message. The screen
   listener displays that message in an error toast.

Important existing validation details to preserve:

- Outer whitespace is ignored for minimum length, matching, and the submitted
  password, even though the fields display the raw input.
- The helper text says the password should contain letters and/or numbers, but
  the code does not enforce a character-category rule. Keyboard work must not
  add such a rule.
- There are no field-level error widgets, Form validators, maxLength input
  restriction, or forced validation before SubmitCreatePassword reaches the
  BLoC.


7. Shared/custom TextField effects on keyboard behavior
-------------------------------------------------------

PasswordInput is the decisive custom component. Its constructor currently
accepts only hint, obscureText, onChanged, and onToggle. It does not forward
textInputAction, onSubmitted, or onEditingComplete to its internal TextField.
Therefore the screen cannot configure Next/Done without a narrow extension to
PasswordInput's API.

PasswordInput also owns the private FocusNode used for the focus-gradient
border. Replacing, externally disposing, or bypassing this node could regress
the border state or cause lifecycle errors. An explicit external FocusNode is
not required for the minimal Next/Done behavior.

The eye icon is a GestureDetector that dispatches only a visibility-toggle
event. It does not intentionally submit, traverse focus, or change the current
text. BLoC rebuilds caused by typing or visibility toggles update the same
StatefulWidget position, so the PasswordInput State and its FocusNode are
normally retained.

DefaultButton affects parity: it suppresses its callback while submitting.
Any keyboard Done path must preserve that protection rather than permitting
repeated update-password requests while the visual Continue button is loading.


8. Safest isolated future integration points
---------------------------------------------

No implementation is included in this audit. The recommended minimal approach
is limited to password_input.dart and create_password_page.dart.

A. Narrowly extend PasswordInput

- Add optional textInputAction and onSubmitted constructor properties.
- Forward them unchanged to the existing internal TextField.
- Leave the private FocusNode, its listener/disposal, onChanged, obscureText,
  visibility toggle, decoration, controller behavior, and all defaults intact.
- Do not add onEditingComplete unless explicit focus-node control becomes
  necessary. Supplying onEditingComplete overrides Flutter's useful default
  completion behavior and creates more lifecycle/focus surface area.

B. First field: Next to the second field

- Pass TextInputAction.next to the first PasswordInput.
- Keep onEditingComplete null. Flutter's default handling for the Next action
  advances the FocusScope to the next focusable control; with the current
  widget/focus order, that is the re-enter-password TextField.
- Do not also call FocusScope.nextFocus from onSubmitted: Flutter processes the
  default Next completion before onSubmitted, so a second manual traversal can
  skip past the second field.
- Add a focused widget test to prove that submitting the first field gives the
  second TextField focus. If future UI changes introduce another focusable
  control between them, explicit focus-node wiring can be considered then,
  but it is a larger and less isolated change today.

C. Last field: Done through the exact Continue action

- Pass TextInputAction.done to the second PasswordInput.
- Create one shared, screen-local callback whose only action is the existing
  dispatch:
  context.read<CreatePasswordBloc>().add(const SubmitCreatePassword()).
- Give that same callback reference to DefaultButton.onPressed and invoke that
  callback from the second input's onSubmitted. Do not copy validation,
  repository calls, toast logic, or navigation into the input callback.
- Preserve DefaultButton's loading lockout for the keyboard path: before the
  Done handler invokes the shared callback, check the current BLoC status and
  do nothing when it is submitting. The status must be read at invocation time
  (context.read<CreatePasswordBloc>().state), not captured from the second
  field's BlocBuilder, because that builder does not rebuild on status-only
  changes.
- The submitted String supplied by TextField.onSubmitted should not be used to
  recreate validation or submission. The existing onChanged events remain the
  source of field state, and SubmitCreatePassword remains the sole entry point
  for validation and the network request.

This approach keeps keyboard concerns in the field wrapper/screen wiring and
reuses the exact existing BLoC event path. It requires no changes to the BLoC,
state, repository, route, validation, toast, or navigation behavior.


9. Regression risks and edge cases to preserve
-----------------------------------------------

- Duplicate submission: repeated Done actions during submitting must not
  bypass the button's existing isLoading lockout and start another request.
- Action parity: Done must dispatch exactly SubmitCreatePassword, including for
  invalid values, so users receive the same warning toasts as a Continue tap.
  Do not gate Done with canSubmit; the button does not use canSubmit.
- Validation order: minimum length, maximum length, then equality must remain
  unchanged.
- Trimming: preserve current trim-before-validation and trim-before-request
  semantics.
- Maximum length: do not add a maxLength formatter or disable submission based
  on the live valid status; the maximum currently runs only on submit.
- Character rules: do not turn the helper copy about letters/numbers into a new
  validation requirement.
- Error/success flow: keep warning toasts for local validation, error toast for
  repository failure, success toast plus context.go(AppRoutes.home) on success.
- Focus styling: retain each PasswordInput's private FocusNode listener so the
  gradient border follows focus correctly when Next moves between fields.
- Visibility toggles: eye-icon behavior, obscured text, entered text, selection,
  and current focus must remain intact.
- Platform IMEs: explicitly setting Next and Done is important because the
  current null action is platform-derived. Tests should verify callbacks and
  focus, not only the keyboard icon label.
- Hardware keyboard/accessibility: field submission should use TextField's
  standard submission hook rather than raw key interception, preserving IME,
  hardware keyboard, and accessibility behavior.
- Keyboard layout behavior: keep resizeToAvoidBottomInset: true,
  ScrollViewKeyboardDismissBehavior.onDrag, and StripedScaffold's existing
  keyboard-open stripe behavior unchanged.
- BLoC builder capture: the confirm-field BlocBuilder rebuilds only for confirm
  text/visibility changes, not submission status. A Done loading guard must
  query live BLoC state when invoked.
- Existing button customization: preserve the configurable buttonLabel and the
  DefaultButton visual/loading behavior.
- Test coverage: add focused widget tests for first-field Next focus transfer,
  second-field Done dispatch, invalid Done using the existing validation path,
  and Done being ignored while submitting. No screen-specific tests currently
  cover these behaviors.


Recommended boundary
--------------------

Future implementation should touch only:

- lib/app/Aliv-Mobile/createPassword/widgets/password_input.dart
- lib/app/Aliv-Mobile/createPassword/view/create_password_page.dart
